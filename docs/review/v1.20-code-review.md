# v1.20 code review — memory that works at night

**Scope.** Spec `docs/issues/mr-robot-v1.20.md`, tickets `docs/issues/mr-robot-v1.20/00–07`, commits `53c8224`, `9aa926d`, `3170388`, `ecdc5d3`, `01b13ce`, `d1b27b7`, `a18101b`, `6129444`, `ebb128d`; ADR 0003; GLOSSARY.md. Code read: `apps/worker/src/robot/duties.ts`, `robot/robot.ts` (alarm, `runTurn`, accounting, memory index, people pages, dream), `robot/idle.ts`, `robot/memory-index.ts`, `agent/platform-step.ts`, `agent/compaction.ts`, `agent/compose.ts`, `plugins/{snapshot,idle,dream,say,memory}.ts`, `places/files.ts`, `member/{member,people}.ts`, `workspace/{workspace,file-history}.ts`, the v1.20 tests, and the DSH packages the fence and the step limits run on.

**Counts.** 5 bugs, 14 risks, 7 drifts, 5 test gaps, 3 notes (34 findings).

**Packages named below.** DSH here is `@deepseek-ai/dsh-tools@0.2.1-rc.2` and `@deepseek-ai/dsh-agent-loop@0.2.1-rc.2`, resolved under `node_modules/.pnpm/` (the two packages are cited by their `lib/index.js`).

**How to read severity.** *bug*: wrong now on the ordinary path. *risk*: wrong when the named condition holds. *drift*: the spec, the ticket and the code disagree. *test gap*: a claim no test exercises. *note*: an observation with consequences but no defect on its own.

## Bugs

### 1. The step fence refuses `run_code`, so every fenced platform step is inert on a default Robot, and its marks still advance

**What.** Code mode is the default execution mode and the default for a new Robot (`apps/worker/src/robot/programs.ts:1124`: `codeMode: true`). In code mode the model may call only `run_code`; the runtime rejects every native tool call ("only `run_code` is callable directly", `@deepseek-ai/dsh-tools/lib/index.js:2614, 3196, 3281`; the presented schema list is filtered to `run_code` at `:2941-2942`). The step fence is a name allow-list and contains no `run_code`: `MEMORY_STEP_TOOLS = new Set(['read', 'write', 'edit', 'glob', 'grep'])` (`apps/worker/src/plugins/snapshot.ts:21`), `DREAM_TOOLS` / `CHIEF_DREAM_TOOLS` (`apps/worker/src/plugins/dream.ts:26,28`). The guard denies the only callable tool before its body (`apps/worker/src/agent/compose.ts:118`, `apps/worker/src/agent/platform-step.ts:48-53`). So on a code-mode Robot, while any fenced step runs, no tool can execute at all.

The consequence is silent loss, because each step still finishes and the code advances its bookkeeping as if the work was done:

- the idle snapshot and the memory sweep (`apps/worker/src/plugins/idle.ts:124-152`) still write `SWEPT_AT` (`:151`) and the memory mark (`:153`), so notes that were never read are marked swept and never swept again;
- the in-Turn snapshot (`apps/worker/src/plugins/snapshot.ts:71-97`) opens the five-tool fence for the rest of the person's Turn, where `run_code` is refused: the person's Turn cannot call any tool until the compaction boundary or the Turn's end;
- the dream (`apps/worker/src/robot/robot.ts:781`) cannot read, write or propose, and `DREAMED_AT` is advanced regardless (`apps/worker/src/plugins/dream.ts:117`), so the evidence is gone for the next night.

This is also a regression against v1.18, where the sweep had no allow-list at all (`git show 0809e70:apps/worker/src/robot/robot.ts`, the sweep block: `agent.followup(...); await agent.whenIdle()`, no guard). Ticket 00 says "No behaviour changes; every existing test stays green".

**Evidence.** `apps/worker/src/agent/compose.ts:118` (guard), `:148` (`presentAs('ptc')`), `apps/worker/src/robot/robot.ts:2052` (`ptcRuntime` when code mode); DSH `dsh-tools/lib/index.js:2614,2941-2942,3196,3281`; every v1.20 test pins `codeMode: false` before exercising a fenced step: `apps/worker/test/snapshot.test.ts:27`, `dreaming.test.ts:27`, `chief-dream.test.ts:38,47`, `memory-sweep.test.ts:25`, `idle.test.ts:29`, `people-pages.test.ts:28`, `memory-search.test.ts:26`.

**Severity:** bug.

### 2. Save as definition publishes the copies unsanitised on a code-mode Robot

**What.** The scrub that removes the owner's private facts from the copies is now a platform step with `tools: MEMORY_STEP_TOOLS` (`apps/worker/src/robot/robot.ts:3886-3892`), so in code mode it cannot edit a single file (finding 1). The code then reads the draft directory and publishes it to the Space library regardless (`:3894-3907`). Before v1.20 the scrub had no tool restriction (same file at `0809e70`: a bare `followup` + `whenIdle`), so it ran in code mode. The result is that every definition saved from a default Robot carries SOUL.md, AGENTS.md, MEMORY.md and skills/ with the owner's data, in a library other Members browse.

**Evidence.** `apps/worker/src/robot/robot.ts:3886-3892` (fenced scrub), `:3894-3907` (publish); `apps/worker/src/plugins/snapshot.ts:21`; ticket 01 closing note: "Moved onto platformStep too: the Save as definition scrub (now with the Workspace file tools only, booked as robot; it was not booked before)".

**Severity:** bug.

### 3. The owner cannot delete or restore a people page, and the delete reports success

**What.** The owner's file routes go through `Robot.deleteFile` and `Robot.restoreFile`, and neither knows about people pages, although `fileContent`, `saveFile`, `fileHistory` and `fileVersion` do. `deleteFile` removes an R2 object that never existed for a page (`apps/worker/src/robot/robot.ts:4102-4111`); the Member row stays, `files()` lists the page again, and the API still answers `{ ok: true }` (`apps/worker/src/edge/api.ts:658-664`). `restoreFile` checks `isTrackedFile`, which does not match `memory/people/<slug>.md` (`apps/worker/src/workspace/file-history.ts:52`; the regex is `^(memory|dreams)\/[^/]+\.md$`), so it throws 404 for a page whose versions the drawer shows with a Restore button (`apps/web/src/components/FileHistoryDrawer.tsx:35,53`, `canRestore={canEdit}` and a page is editable, `apps/worker/src/robot/robot.ts:3796`).

GLOSSARY line 35: "Only the Member and, when merging two pages of one person, Mr. Robot delete one." The only way to delete is that delete button. The member-file docs also promise the history: "The owner can restore a version" (`apps/worker/src/docs/memory-and-files.ts:40`).

**Evidence.** `apps/worker/src/robot/robot.ts:3934-3940`, `:4102-4111`; `apps/worker/src/workspace/file-history.ts:52`; `apps/worker/src/edge/api.ts:658-664`; the delete/restore paths that *were* adapted: `apps/worker/src/robot/robot.ts:3791-3833, 3911-3932`; test gap: `apps/worker/test/people-pages.test.ts:70` edits a page but never deletes or restores one, and `chief-dream.test.ts:84-85` only proves a *Robot* is refused.

**Severity:** bug.

### 4. The dream's tokens are priced at the Robot's model, not the dream model

**What.** The dream runs on its own route (`apps/worker/src/robot/robot.ts:742, 1995-1997, 2651-2655`), but the Turn's accounting prices every event with the *stored* config's model: `const price = (await this.space().modelList()).find((option) => option.provider === config.model.provider && option.model === config.model.model)?.price` (`:1945`). `accountTurn` is called with the source `memory` for the dream (`:1509`), so the source is right and the amount is wrong. With `dreamModel` set (the point of dm-ox7j: "reflection is cheap") the dream's cost is billed at the Robot's model price; if the Robot's model has no price entry the dream is billed 0. The same price feeds the monthly counters the spend limit reads (`apps/worker/src/robot/programs.ts:442-447`). The test cannot see it: the stub models carry no price (`apps/worker/test/dreaming.test.ts:96` only asserts `memory > 0`).

**Evidence.** `apps/worker/src/robot/robot.ts:1944-1949`, `:1507-1509`, `:2651-2655`; `apps/worker/src/robot/programs.ts:435-461`. The composition the dream runs in is built from the dream route (`robot.ts:1995-1997, 2004-2005`), so the tokens that reach the counter are the dream model's while the price is the Robot's.

**Severity:** bug.

### 5. A Turn that ends before the snapshot's third boundary suppresses the snapshot of the *next* compaction

**What.** `TurnSnapshot.finish()` sets `SNAPSHOT_TAKEN = sessionId` (`apps/worker/src/plugins/snapshot.ts:116`) and it is called unconditionally at every Turn's end (`apps/worker/src/robot/robot.ts:822`), even when the snapshot ran out with the Turn and no compaction followed. It also moves the memory mark to the Turn's end (`snapshot.ts:115`). `beforeCompaction` then returns false while `SNAPSHOT_TAKEN` names the live session (`snapshot.ts:86-87`), and `compacted()` — the only thing that clears it (`snapshot.ts:100-102`, wired at `robot.ts:2042`) — does not run because no compaction did. So the next pressure compaction, in the next Turn, summarises the context with no snapshot before it. That is exactly the loss dm-kg1p exists to prevent; the spec's only skip rule is "no event in the chapter since the last snapshot or sweep" (`docs/issues/mr-robot-v1.20.md:89`), and here events did happen.

The ordinary way in: the steer reaches the model one step after the boundary, the model writes the note and ends the Turn in its next step; the third boundary never comes.

**Evidence.** `apps/worker/src/plugins/snapshot.ts:71-97, 104-118`; `apps/worker/src/robot/robot.ts:821-823`, `:2037-2043`; no test ends a Turn while the snapshot is still running (`apps/worker/test/snapshot.test.ts:46-84` always lets the compaction run).

**Severity:** bug.

## Risks

### 6. A pressure compaction during a dream closes the dream's tool fence for the rest of the night

**What.** The dream opens the fence directly with `fence.open(...)` and never calls `enter()` (`apps/worker/src/robot/robot.ts:781`), so `StepFence.inStep()` is false. `TurnSnapshot.beforeCompaction` guards only `host.step.fence.inStep()` (`apps/worker/src/plugins/snapshot.ts:75`), so a pressure compaction inside the dream starts a snapshot, which re-opens the fence with five tools (`snapshot.ts:93`) and, at its finish, calls `fence.close()` (`snapshot.ts:110`). From that point the dream has no allow-list: `say`, `web_fetch`, `robot_send`, `subagent`, Box, Hosts and — for Mr. Robot — `robot_file_write` (the tool ticket 06 says his dream is refused, `dream.ts:28`) are all callable, and `dreamArgsCheck`'s one-ask closure is gone with the fence. `writeAs(undefined)` at `snapshot.ts:111` also makes the dream's later writes "the Robot" in the file history (`apps/worker/src/robot/robot.ts:344`).

The dream is the one Turn whose chapter is fresh, but a Robot with a small `contextBudget` (128k default, `programs.ts:1096`; tests use 8k) or a large MEMORY.md and daily notes can cross the pressure threshold within its 12 steps, since the budget adapter reports the budget as the model window (`apps/worker/src/agent/budget.ts:64-69`) and pressure compacts at ~85% of it (`@deepseek-ai/dsh-compaction-basic` `resolveCompactSpec`).

**Evidence.** `apps/worker/src/robot/robot.ts:781, 803-808, 2037`; `apps/worker/src/plugins/snapshot.ts:75, 93, 109-111`; `apps/worker/src/plugins/dream.ts:28, 64-75`; dm-0ylj, dm-w15l; every dream test turns code mode *and* pressure off (`dreaming.test.ts:27` runs 7 steps without a compaction).

**Severity:** risk (condition: a pressure compaction inside the dream). It defeats dm-0ylj ("no tool that acts on the world") and the cross-Robot write refusal of dm-w15l.

### 7. The in-Turn snapshot's fence outlives its steps into the safety net, so the safety net cannot say

**What.** `speakUp` runs at `apps/worker/src/robot/robot.ts:810`; `turnSnapshot.finish()` — the only thing that closes the snapshot fence in the Turn path — runs at `:822`, after it. The safety net's `platformStep` passes no `tools` (`apps/worker/src/plugins/say.ts:50`), so `platformStep` neither opens nor closes the fence (`apps/worker/src/agent/platform-step.ts:95,103`), and the snapshot's five-tool allow-list is still in force. The safety net's `say` is refused (`platform-step.ts:48-53`). An owner's Turn then falls back to its last assistant text, if any; a Turn nobody asked for ends silent by design.

The same window means the person's Turn cannot `say` for as long as the snapshot is open — and the snapshot's instruction says "Do not reply to the owner" (`apps/worker/src/plugins/snapshot.ts:23`), which steers the model to end the Turn without one.

**Evidence.** `apps/worker/src/robot/robot.ts:803-825`; `apps/worker/src/plugins/say.ts:46-58`; `apps/worker/src/agent/platform-step.ts:88-111`; `apps/worker/src/plugins/snapshot.ts:22-23, 93`; the test only checks the say *after* the compaction (`apps/worker/test/snapshot.test.ts:69-71`).

**Severity:** risk (condition: the Turn ends while the snapshot fence is open, i.e. fewer than three compaction checks after the steer).

### 8. A due duty that refuses while the Robot is busy leaves the alarm in the past, and `rearm` does not clamp

**What.** `dreamDuty.run` returns without advancing `DREAM_AT` when the Robot is not idle: `if (due > now || !host.idleNow()) return` comes *before* `store.set(DREAM_AT, host.nextDreamHour(now))` (`apps/worker/src/plugins/dream.ts:109-112`). `dreamCloseDuty` has the same order (`apps/worker/src/plugins/idle.ts:179-184`), and so does `idleDuty` (`:75-83`). `rearm` takes `Math.min(...candidates)` with no floor (`apps/worker/src/robot/programs.ts:1330-1339`), so it calls `setAlarm` with a moment in the past. The alarm fires again at once; `runAlarm` repeats `fireTasks` and `releaseParked` (Space RPCs) and all ten duties, and re-arms in the past again. The loop lasts as long as the Turn does.

The condition is ordinary: an alarm at 03:00 while a Turn runs (a scheduled Task at 03:00, a message at 03:00), or any alarm at the moment a Wake-up has just been queued — `runAlarm` starts the Turn itself before the duties run (`apps/worker/src/robot/robot.ts:624-627`), so `idleNow()` is false and the due duties refuse.

**Evidence.** `apps/worker/src/plugins/dream.ts:107-112`; `apps/worker/src/plugins/idle.ts:179-184`; `apps/worker/src/robot/robot.ts:363` (`idleNow`), `:618-629`; `apps/worker/src/robot/programs.ts:1320-1339`; ADR 0003: "the next alarm ... is the earliest of the core's moments ... and the duties' earliest nextAt."

**Severity:** risk (condition: a due duty at a moment when a Turn runs or a Wake-up is queued).

### 9. A Wake-up during an idle platform step shares the step's fence, author and cancel counter

**What.** `idleNow()` is checked once, when the duty starts (`apps/worker/src/robot/robot.ts:363`; `apps/worker/src/plugins/idle.ts:78, 183`). `wake()` deletes the idle plan and drains (`apps/worker/src/robot/programs.ts:157-168`), and `pump` starts the Turn at once (`robot.ts:702-736`) while the idle `platformStep` is mid-await. Then, on the *same* agent and session: the person's Turn's tool calls are checked against the step's allow-list (`platform-step.ts:48-53`); its file writes are attributed to `{ kind: 'sweep' }` / `{ kind: 'snapshot' }` because `writeAs` is in force (`platform-step.ts:96, 104`); the step's counter counts the person's step starts and calls `agent.cancel(..., { keepInbox: true })` at the limit (`platform-step.ts:91-93`), aborting the person's work; and `agent.whenIdle()` makes the step wait for the whole Turn. `idleCompact` checks `activeTurn()/pendingWakeups()` only before `compactNow` (`plugins/idle.ts:154`), not before the snapshot or the sweep.

**Evidence.** `apps/worker/src/agent/platform-step.ts:88-111`; `apps/worker/src/plugins/idle.ts:78, 109-162`; `apps/worker/src/robot/robot.ts:363, 702-736`; `apps/worker/src/robot/programs.ts:157-168`.

**Severity:** risk (condition: a Wake-up arrives between the `idleNow()` check and the end of the step).

### 10. A restart in the middle of a platform step leaves its instruction in the durable inbox, to be replayed as a Wake-up of the next Turn

**What.** `platformStep` hands the instruction over with `agent.followup(step.instruction)` (`apps/worker/src/agent/platform-step.ts:98`). The DSH inbox is a durable projection over `agent/inbox/spliced` events (`@deepseek-ai/dsh-agent-loop/lib/index.js:16-58, 203-206`), and the agent resumes the same session after a restart. If the isolate dies between the followup and the claim, the instruction is still queued for `next-turn` and is read at the next Wake-up: the memory-step instruction ("Then end", "Do not reply to the owner") reaches the person's Turn with no fence, no step limit and no `writeAs`, and the step's usage is never booked because `platformStep` never returns. The same holds for the idempotence of the idle plan step, which was already removed from the plan before the step ran (`plugins/idle.ts:79-81`).

**Evidence.** `apps/worker/src/agent/platform-step.ts:87-111`; `@deepseek-ai/dsh-agent-loop/lib/index.js` inbox projection; `apps/worker/src/plugins/snapshot.ts:22` (the instruction), `plugins/idle.ts:79-81` (the plan step consumed first).

**Severity:** risk (condition: the Durable Object is evicted or restarted while a platform step runs).

### 11. An in-Turn snapshot books the rest of the Turn under the memory source

**What.** `finish()` records the range `[startSeq, storedLength())` (`apps/worker/src/plugins/snapshot.ts:112-115`) and `accountTurn` books every event inside a range as `memory` (`apps/worker/src/robot/robot.ts:1934-1940`). When the snapshot ends at the Turn's end instead of at a compaction boundary, the range covers everything from the pressure decision to the end of the Turn: the person's remaining work and the safety net's tokens (the safety net runs at `:810`, `finish` at `:822`). The Turn's cost is then attributed to tending memory, which the cost breakdown shows as a separate line and dm-pifl calls "the cost of tending memory is one line".

**Evidence.** `apps/worker/src/plugins/snapshot.ts:104-118`; `apps/worker/src/robot/robot.ts:809-825, 1931-1951`; `apps/worker/test/snapshot.test.ts:78-80` asserts only that both sources are non-zero.

**Severity:** risk (condition: the snapshot finishes at the Turn's end; see finding 5).

### 12. An unavailable dream route fails the night's Turn and pushes "blocked" at 03:00, every night

**What.** `dreamRoute` returns the configured route without checking it against the Robot's chain, the Space's model list or the owner's credentials (`apps/worker/src/robot/robot.ts:2651-2655`); `pump` picks the chain entry for the *Robot's* model only (`:728`, `:1832`). A `dreamModel` naming a provider with no credential (or a model the provider no longer serves) makes the dream Turn fail; `failed()` then sets `failed-wakeup` for "Try again" and calls `notifyMembers('blocked', ...)` (`robot.ts:1907-1926`). Nothing in the dream duty catches this and nothing stops the next night from doing it again.

**Evidence.** `apps/worker/src/robot/robot.ts:2651-2655, 728, 1832-1868, 1907-1926`; `apps/worker/src/robot/programs.ts:543-544` (settings accept any route); `apps/worker/test/dreaming.test.ts:51` only sets a route the stub serves.

**Severity:** risk (condition: a dream model route that cannot run).

### 13. A dream that had to wait runs outside its hour, ahead of the person's messages, and is not re-gated by `dreaming`

**What.** The dream is a queued platform Wake-up with `{ dream: true }` (`apps/worker/src/robot/robot.ts:322-327`). If it cannot start — the Robot is blocked by its spend limit (`pump`, `:720`), or every chain entry is unavailable (`:722`, `:728`) — it waits in the queue. When it can start it runs at whatever time that is, and in FIFO order, so a message the owner sent at 09:00 waits behind a 12-step dream that declares "it is night". `runTurn` decides the dream from the payload alone (`:741`); turning dreaming off between the enqueue and the run does not stop it.

**Evidence.** `apps/worker/src/robot/robot.ts:316-327, 720-736, 741`; `apps/worker/src/plugins/dream.ts:108-118`; `apps/worker/src/robot/programs.ts:435-461`.

**Severity:** risk (condition: a dream queued while the Robot cannot run, or dreaming switched off after enqueue).

### 14. The first 03:00 after the key is absent is always skipped

**What.** Both duties plan with `store.get(KEY) ?? nextDreamHour(now)` and, when the key is absent at the moment the alarm fires, store `nextDreamHour(now)` and return without doing the work (`apps/worker/src/plugins/dream.ts:109-110`; `apps/worker/src/plugins/idle.ts:181-182`). `nextRun` for a daily rule is strictly after `after` (`apps/worker/src/robot/schedule.ts:139`), and `dreamDuty.nextAt` without a key returns that same moment, so the alarm is set at 03:00 and the work is postponed to the next 03:00. A Robot created (or a Durable Object first woken) between midnight and 03:00 with no other alarm loses its first night's close and dream. The tests never see it because they write the key first (`apps/worker/test/worker.ts:592-597, 648-651`; `dreaming.test.ts:54-57`).

**Evidence.** `apps/worker/src/plugins/dream.ts:107-112`; `apps/worker/src/plugins/idle.ts:178-184`; `apps/worker/src/robot/schedule.ts:132-143`; dm-76yv, dm-hx44.

**Severity:** risk (condition: the keys are absent when the 03:00 alarm fires).

### 15. Changing the owner's time zone leaves the stored dream hour on the old zone for a night

**What.** `DREAM_AT` and `DREAM_CLOSE_AT` are absolute timestamps computed once and read back from kv (`plugins/dream.ts:107`; `plugins/idle.ts:178`). `timeZoneChanged` updates the config and re-arms but does not touch either key (`apps/worker/src/robot/robot.ts:4031-4041`). After a move, the next night's close and dream happen at the old zone's 03:00 — up to 24 hours off for a large move, and the "night" can fall in the Robot's busiest hour. DST itself is safe: `scanDays` computes each target day's local time with the zone (`schedule.ts:123-144`).

**Evidence.** `apps/worker/src/robot/robot.ts:4031-4041`; `apps/worker/src/plugins/dream.ts:107`; `apps/worker/src/plugins/idle.ts:178`; no test moves a zone with a dream hour stored (`apps/worker/test/time-zone.test.ts` has no dream case).

**Severity:** risk (condition: the owner's zone changes between two dream hours).

### 16. The night's evidence can be lost before the dream runs, and `DREAMED_AT` is advanced first

**What.** `dreamDuty.run` sets `DREAMED_AT = now` before it enqueues the Turn (`apps/worker/src/plugins/dream.ts:114-118`), and `dreamEvidence` swallows every failure: `listTasks(...).catch(() => ({ tasks: [] }))`, `reachable(...).catch(() => [])`, `files().catch(() => [])` (`apps/worker/src/robot/robot.ts:2662-2674`). A transient Space or R2 failure on the night of the dream yields an empty evidence list, the skip rule fires, and the notes, Attempts and Asks of the day are never offered again. A dream Turn that fails or is interrupted after the enqueue also consumes the window.

**Evidence.** `apps/worker/src/plugins/dream.ts:113-118`; `apps/worker/src/robot/robot.ts:2658-2675`; `apps/worker/src/plugins/dream.ts:40`.

**Severity:** risk (condition: one failed RPC in the evidence gathering, or a failed dream Turn).

### 17. `writtenBy` walks and HEADs every tracked file twice per idle cycle

**What.** Both the idle snapshot's and the sweep's Trajectory records list the whole Workspace and read one R2 object per tracked file to find the author (`apps/worker/src/plugins/idle.ts:115-123, 134, 149`; `apps/worker/src/robot/robot.ts:1954-1963`). For a Robot with a year of daily notes this is 365+ `list` entries and 365+ `head` calls per memory step, twice per idle compaction, before the compaction itself. The same helper is backgrounded for every in-Turn snapshot (`robot.ts:253`). Nothing in the scale test measures it.

**Evidence.** `apps/worker/src/plugins/idle.ts:115-123`; `apps/worker/src/robot/robot.ts:1954-1963`; `apps/worker/test/scale.test.ts` has no idle compaction in its measurements.

**Severity:** risk (condition: many daily notes and an idle cycle).

### 18. Two Robots of one Member can lose one another's facts on a people page

**What.** A page is written as a whole file: the tool reads it and writes it back (`apps/worker/src/places/files.ts:171-181`; the `edit` tool reads then writes), and the Member stores the last full content (`apps/worker/src/member/member.ts:864-875`). Two Robots editing one page at the same time are a lost update: the later write drops the earlier Robot's lines, and the file history keeps the dropped version only as a version. INDEX.md itself is safe — it is regenerated from all rows inside the Member DO with synchronous SQL after each write (`member.ts:858-862`), and the DO serialises it, so it cannot lose a row.

**Evidence.** `apps/worker/src/places/files.ts:171-181`; `apps/worker/src/member/member.ts:858-875`; `apps/worker/test/people-pages.test.ts:47-53` writes sequentially only.

**Severity:** risk (condition: concurrent writes to one page).

### 19. Dreaming off in the Space still wakes every Robot at 03:00 and still closes its chapter

**What.** `nextAt` for both duties gates on `config().dreaming === false` only; the Space default is consulted only inside `run` (`apps/worker/src/plugins/dream.ts:107, 113`), and the close never consults it at all (`apps/worker/src/plugins/idle.ts:178-180`). A Space admin who sets `defaultDreaming: false` stops the dream Turn but keeps a nightly 03:00 alarm on every Robot (each a cold-start cost) and a nightly snapshot + sweep + compaction for any Robot whose chapter has events (`idleCompact(host, false)` with the floor off, `plugins/idle.ts:188`). dm-buya: "dreaming on by default for every Robot with a per-Robot switch and a Space default"; the glossary says the dream hour is when "a chapter still open is closed the same way".

**Evidence.** `apps/worker/src/plugins/dream.ts:107,113`; `apps/worker/src/robot/robot.ts:319`; `apps/worker/src/plugins/idle.ts:173-190`; the test `dreaming.test.ts:122-126` sets the Space default off and asserts only that no *request* is made.

**Severity:** risk (condition: the Space default off with per-Robot `dreaming` null).

## Drift

### 20. Every step limit is one step short, because the cancel fires at the start of the limit-th step

**What.** `platformStep` cancels when `++steps >= step.steps` on `step/start` (`apps/worker/src/agent/platform-step.ts:91-93`), and the dream does the same with `DREAM_STEPS` (`apps/worker/src/robot/robot.ts:784-786`). DSH appends `step/start` *before* the model call of that step (`@deepseek-ai/dsh-agent-loop/lib/index.js:970-980`), so the request of step N never happens: a "3 model step" snapshot gets 2, and a "12 model step" dream gets 11.

**Evidence.** `apps/worker/src/agent/platform-step.ts:88-93`; `apps/worker/src/robot/robot.ts:783-786`; `apps/worker/src/plugins/snapshot.ts:19`; `apps/worker/src/plugins/dream.ts:20`; ADR 0003: "`steps`: the model steps at most"; `apps/worker/src/docs/dreaming.ts:13`; `apps/worker/src/docs/memory-and-files.ts:32`.

**Severity:** drift.

### 21. The dream is not "its own chapter"

**What.** The spec's Implementation Decisions say "The dream is a Turn with cause dream, its own chapter, step limit 12" (dm-7s7w). No code opens or marks a chapter for the dream: it runs in the chapter the live session has (`apps/worker/src/plugins/dream.ts:8` writes this down as the contract), and the dream-hour close only compacts when there are events since the last compaction (`robot.ts:332-336`, `plugins/idle.ts:185`). The chapter table has no cause (`store.chapters.openChapter`), so the Trajectory cannot show "the dream's chapter" either; it shows the Turn in whatever chapter was live.

**Evidence.** `apps/worker/src/plugins/dream.ts:5-16`; `apps/worker/src/robot/robot.ts:329-337, 741-744`; `docs/issues/mr-robot-v1.20.md:94`; `apps/worker/test/dreaming.test.ts` never asserts a chapter for the dream.

**Severity:** drift.

### 22. The dream's skip rule counts only Attempts that failed or were skipped, against a spec that says "no Attempt closed"

**What.** dm-hx44 and the Implementation Decisions say the dream is "skipped when no daily note changed and no Attempt closed and no Ask was answered" (`docs/issues/mr-robot-v1.20.md:65,94`); dm-pzxk says the dream reads "the Attempts that failed or were skipped". The code implements the narrower rule for both: the evidence only collects failed/skipped Attempts (`apps/worker/src/robot/robot.ts:2669-2670`) and the skip rule is `notes.length === 0 && attempts.length === 0 && answered === 0` (`apps/worker/src/plugins/dream.ts:40`). A day of successful Attempts and closed chapters with no note edit is not dreamt about. The chapters the evidence computes are never used by the skip rule.

**Evidence.** `apps/worker/src/plugins/dream.ts:40, 43-61`; `apps/worker/src/robot/robot.ts:2667-2674`; `apps/worker/src/docs/dreaming.ts:8` ("no Attempt closed"); `docs/issues/mr-robot-v1.20.md:65,67,94`.

**Severity:** drift.

### 23. The docs and the fences disagree about the memory steps' tools

**What.** `docs/memory-and-files.md`: "It has 3 model steps and only the file tools on the Workspace" (`apps/worker/src/docs/memory-and-files.ts:32`), and "The file tools are read, write, edit, delete_file, glob and grep" (`:59`). **Evidence.** `apps/worker/src/docs/memory-and-files.ts:32,59`; `apps/worker/src/plugins/snapshot.ts:21`; `apps/worker/src/docs/dreaming.ts:33`; `apps/worker/src/plugins/dream.ts:28`.

## The questions asked, settled

1. **Can a duty run while a Turn runs, or re-enter itself?** A duty runs while a Turn runs: the alarm's Turns live in `ctx.waitUntil`, so the handler returns and the next alarm can interleave; the guard is `idleNow()`, checked once (findings 8, 9). A duty does not re-enter itself concurrently: `runAlarm` awaits `duties.run` and DSH serialises alarm handlers; the exception is the past-moment re-arm loop (finding 8). A DO restart mid-duty leaves the step's instruction in the durable inbox (finding 10).
2. **Can the snapshot steer end or corrupt the person's Turn, or run inside another platform step?** Yes to the first two: the steer says "Do not reply to the owner" and the fence removes `say` and every non-file tool for the rest of the Turn; the fence can outlive the steps into the safety net (findings 7, 5). It cannot start inside a `platformStep` — `inStep()` stops it (`snapshot.ts:75`) — but the dream is not a platform step, so it starts inside the dream (finding 6).
3. **Can the dream reach a tool outside its contract, send anything, or run on a Robot with dreaming off?** Not through code mode (the fence blocks everything, finding 1); yes after a pressure compaction closes the fence, including `say` and Mr. Robot's `robot_file_write` (finding 6). The dream is enqueued only when `dreamingOn()` is true, but a queued dream is not re-gated (finding 13).
4. **Does the dream's cost land under the memory source and respect the spend limit?** The source is memory (`robot.ts:1509`), the price is the Robot model's (finding 4), so both the billed cost and the spend-limit check are wrong when the dream model differs. A dream held back by the limit runs later (finding 13).
5. **Can two Robots race on INDEX.md or a page?** INDEX.md no (finding 34); a page yes, last write wins (finding 18).
6. **Is the FTS index consistent after a restore, a delete, a rename, and bounded on the first Turn?** Restore and delete go through `makeWorkspace`'s `onChange` (`workspace.ts:162-179`, `robot.ts:2684-2691`), so both reindex at once, and the tests cover them (`memory-search.test.ts:83-92`). Rename: there is no rename of a memory file (Pages rewrite in place, `robot.ts:3707-3711`), so nothing to test. Bounded: 100 files per catch-up, tested at 150 (`memory-search.test.ts:101-112`); the first Turn after the upgrade indexes the oldest 100 by key order, so a recent note is not searchable until a later Turn (design, not defect).
7. **Does memory_search leak Space or Member files?** No. The Member files are the Robot owner's own (`robot.ts:2718-2721`), SPACE.md is the Space's shared file, and no route exposes `memorySearch` outside the agent (`apps/worker/src/edge` has no endpoint). Setup Robots mount the Memory plugin with `tools: false` (`robot.ts:2132`), so they have no `memory_search` at all.
8. **Does the dream hour use the owner's zone and survive DST?** It uses `config.timeZone`, which follows the owner's profile, and `nextRun` computes each day's local time in the zone, so DST is safe; a zone *change* leaves the stored hour on the old zone for one night (finding 15). Only UTC is tested (finding 29).
9. **Does warming-then-closing honour "never while anything is queued"?** At entry, yes (`idleNow()`, `planIdle`); after entry, a Wake-up can arrive mid-step and shares the step's fence, author and cancel counter (finding 9), and the compaction itself is skipped when a Wake-up is queued (`plugins/idle.ts:154`).
