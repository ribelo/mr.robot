# Cross-cutting review, v1.15 to v1.20 (f55f2fb..ebb128d)

Read-only review of the Worker, edge, infra, protocol and tests as implemented between f55f2fb and ebb128d. Specs and tickets were read from docs/issues/mr-robot-v1.15.md to v1.20.md and their ticket closing notes (the implementer's decisions); the glossary and ADR 0003 were the vocabulary. Evidence is a path:line, a quoted ticket/spec sentence, or a test name.

State when sampled: `pnpm typecheck` is clean, and the whole suite ran green once (122 files, 728 tests, ~151 s). Nothing below claims a test currently fails; the flaky findings are about why the two tests the implementer named can fail under load, which one green run cannot show.

## Findings

1. **Secret redaction stops at the Turn boundary, so a secret repeated by the model later is stored in plaintext.** `SqliteSessionLog` rewrites each event before it is stored, but the redactor is built from the *running* Turn's secrets only (`redact: (json) => maskSecrets(json, this.turnSecrets)`, apps/worker/src/robot/robot.ts:2022) and `turnSecrets` is cleared when the Turn ends (robot.ts:813-817). The values loaded at boot for masking views are held in `secretValues`, which is used by `mask()` (robot.ts:3643-3645, 4177-4183) but is never passed to the store. So in any Turn after the one that fetched a value with `secret_get`, an event that repeats that value is written verbatim to `session_event` (apps/worker/src/agent/session-log.ts:181), folded into the stored chat in the same transaction (session-log.ts:185; robot.ts:2024-2026), indexed by the conversation FTS (session-log.ts:184) and, once the chapter ages out, uploaded whole to R2 (apps/worker/src/robot/cold-chapters.ts:48-55). The conversations' own views mask it on screen (apps/worker/src/robot/views.ts:211-226), which hides the leak from the owner. The same redactor also ignores values shorter than three characters (apps/worker/src/agent/tools/secrets.ts:41), so a two-character secret is stored even in the Turn that fetched it. *Severity: risk* (a secret the model carries in context and repeats in a later Turn ends up in the log, the chat, the FTS index and the cold-chapter archive; it depends only on the model restating it).

2. **Auto review sends the whole unredacted in-memory history to the reviewer's provider before every allowed tool call.** The reviewer input is built from `session?.snapshotEvents()` with no truncation (apps/worker/src/agent/auto-review.ts:78-104) and the plugin passes it straight to an adapter on the reviewer route (apps/worker/src/plugins/auto-review.ts:41-55). The gate calls the reviewer once per allowed call (apps/worker/src/agent/ask-gate.ts:196-199). Two consequences. Cost: a Turn with *n* allowed calls sends 1+2+...+n model messages of history to the reviewer; on a 128k context the review cost is quadratic in the Turn and is not capped per Turn (only the monthly limit catches it, at the next Turn boundary). Egress: the in-memory events are the unredacted ones (redaction happens only at write, finding 1), and the reviewer route may be a different provider chosen by the Space admin (`config.reviewer ?? space.defaultReviewer ?? config.model`, apps/worker/src/robot/robot.ts:380), so a secret fetched earlier in the Turn is sent to that provider, outside the Space. *Severity: risk* (cost and secret egress, both under the ordinary condition of Auto review being on).

3. **A removed Member's Shared Pages stay public.** `remove` marks the Member removed, unassigns their Tasks, ends their Threads, pauses their Robots and disconnects them (apps/worker/src/space/space.ts:222-231); it never touches the Member Durable Object's `shared_page` rows and never deletes their Robots. `/p/<token>` only asks the Member DO for the share (apps/worker/src/edge/shared-pages.ts:46-54) and the Robot for its HTML (apps/worker/src/robot/robot.ts:3725-3748), neither of which consults the owner's or the Robot's status. Removal (and Pause) therefore keeps every shared link live, and the removed person's own Members page is the only place Stop sharing was reachable from. By contrast a deleted Robot is destroyed with its Workspace (robot.ts:464-482), so only the deletion path revokes by accident. *Severity: risk* (data exposure whenever a Member is removed with an open share).

4. **The dream-hour close ignores the Space's `defaultDreaming`, so turning dreaming off at the Space does not stop the nightly model cost.** The close's gate is `host.store.config()?.dreaming === false` (apps/worker/src/plugins/idle.ts:178, 180) and the duty is registered with that literal check (apps/worker/src/robot/robot.ts:329-337); `dreamingOn()`, which does read the Space default (robot.ts:319), is used only by the dream duty. The Space default is `true` unless set (apps/worker/src/space/space.ts:308-310), and the settings UI exposes it (spec v1.20 "Settings. dreaming: boolean (default true)"). A Robot created without its own `dreaming` therefore runs the snapshot, the sweep and a compaction at 03:00 whenever its chapter has events since the last compaction, even with the Space's `defaultDreaming` off. The code's own comment says "A Robot with dreaming off has no dream hour" (idle.ts:171). *Severity: drift* (spec and code disagree) with a cost effect.

5. **A Robot busy at the dream hour hot-loops the alarm until it is idle.** `rearm` sets the alarm to the minimum of the pending moments with no floor at "now" (apps/worker/src/robot/programs.ts:1330-1339), and both dream duties return without moving their moment when they are due but the Robot is busy: dream-close leaves `dream-close-at` in the past (apps/worker/src/plugins/idle.ts:183-184) and the dream leaves `dream-at` in the past (apps/worker/src/plugins/dream.ts:111-112). `Duties.nextAt` then returns that past moment again (apps/worker/src/robot/duties.ts:38-44), the alarm fires immediately, `runAlarm` does its core work (Task fetch, parked release, drains: apps/worker/src/robot/robot.ts:618-628) and re-arms to the past again. The duty's own comment says "A busy Robot skips that night" (idle.ts:184-185), but nothing skips it: from 03:00 until the Turn ends the Durable Object is spun in a tight loop, each iteration making Space RPCs. *Severity: bug* (any Turn — or a Box/Host job's Turn — spanning 03:00 triggers it).

6. **The dream's tool allow-list is a single slot, and a snapshot during the dream can reopen the Robot's whole tool surface.** The dream opens the fence with `this.fence.open(...)` and closes it after the Turn (apps/worker/src/robot/robot.ts:779-787, 803-807) without `StepFence.enter()` (apps/worker/src/agent/platform-step.ts:27-33), so `inStep()` is false while the dream runs. `TurnSnapshot.beforeCompaction` only declines to start when `fence.inStep()` is true (apps/worker/src/plugins/snapshot.ts:74-75); a pressure compaction in the dream would start a snapshot, which opens its own allow-list and, in `finish()`, calls `fence.close()` (snapshot.ts:108-117), erasing the dream's restriction for the rest of the Turn. The dream then holds the Robot's grants again, and its instruction ("no tool that touches the world") is the only guard left. *Severity: risk* (needs a compaction during the dream; the contract in docs/issues/mr-robot-v1.20/05-dreaming.md says the allow-list "holds", and ADR 0003 treats the fence as the mechanism).

7. **The admin browser probe spends Browser Rendering money per request and is not counted or capped.** `POST /api/admin/browser-probe` (apps/worker/src/edge/api.ts:291-295) calls `probe`, which opens Browser Run, loads any URL the caller gives, waits up to 20 s, screenshots it and returns 600 characters of page text (apps/worker/src/browser/probe.ts:23-48). No `recordUsage`, no `checkLimits`, no rate limit, so the page never shows the cost and the Robot's or Member's limits never see it. It is also a read primitive on arbitrary hosts from Cloudflare's network with the response echoed back. *Severity: risk* (admin-only, but cost is unbounded per request and invisible).

8. **Host pairing is open to the internet with no rate limit, and the host token waits in plain text in the Space's storage.** `/api/host/pair/start` takes an anonymous POST and writes a `host_pairing` row (apps/worker/src/index.ts:47-52; apps/worker/src/space/space.ts:735-740); cleanup of old rows only happens on the next start (space.ts:738). `approvePairing` stores the freshly minted host token in the clear for up to 15 minutes (space.ts:750-757) and `pollPairing` hands it to anyone who knows the code (space.ts:760-767). The code has ~45 bits (space.ts:737), so guessing is not the issue; storage growth and the plaintext token are. Also, any signed-in Member can approve any pending code (the route only checks sign-in, apps/worker/src/edge/api.ts:373-374), binding the Host to the approver rather than to whoever started pairing. *Severity: risk* (unauthenticated write path, unauthenticated storage growth, a token at rest).

9. **The Box's door reads an unbounded body before validating anything.** `boxChannel` calls `await request.text()` with no size limit (apps/worker/src/index.ts:33-38) on a path outside Access; the signature check happens first, so only a holder of a live Box token can send it, but `ws` is Robot-controlled code (a Box script) and a single request can buffer arbitrary bytes in the Worker. The reply also carries presigned URLs without `cache-control: no-store` (index.ts:38). *Severity: note* (needs a live Box token; memory DoS from a Robot's own Box).

10. **Login entries stored before v2 are readable by `secret_get`, against the glossary's "the password never reaches the Robot".** `parseEntry` turns any value that is not the v2 JSON into `{ username: '', password: text, websites: [], allowRead: true }` (apps/worker/src/platform/logins.ts:20-29), and `secret` returns the password for any entry with `allowRead` (apps/worker/src/robot/programs.ts:999-1002). The glossary says of Login entry: "filled into matching pages without the password reaching the Robot's program" (GLOSSARY.md:59) and of Credential request: "The password never reaches the Robot" (GLOSSARY.md:64); the v1.15 ticket says "The password never reaches the Robot's program; login_fill is unchanged" (docs/issues/mr-robot-v1.15/05-request-credential.md). An old deployment's stored passwords are therefore handed to the model once the secrets group is granted, and `login_fill` cannot use them either (no websites, so `entryMatches` always refuses, logins.ts:58-61). *Severity: drift* with a security effect on upgraded deployments.

11. **The memory steps and cache warming spend model money without consulting the spend limit first.** `platformStep` has no limit check (apps/worker/src/agent/platform-step.ts:88-110), and `idleCompact` runs the snapshot, the sweep and the compaction before any `checkLimits` (apps/worker/src/plugins/idle.ts:109-161); `warmCache` likewise just streams and records (idle.ts:89-103). The idle and dream duties are scoped `active`, so a blocked Robot does not run them, but a Robot under the limit on its last Turn can spend past it in a nightly close or a warming burst and only be blocked at the next Turn's start (apps/worker/src/robot/programs.ts:435-461). Bounded per event (3+4 steps and one compaction), not per month. *Severity: risk* (cost overshoot after the cap).

12. **The PDF spend gate is bypassed for every non-active Robot, and the "day" is a rolling 24 hours.** `pagePdf` asks `checkLimits()` (apps/worker/src/robot/robot.ts:3760), which returns false immediately unless the status is `active` or `blocked` for the limit (apps/worker/src/robot/programs.ts:439). A `paused` Robot — precisely the state an owner uses to stop a Robot — still renders PDFs from its own Pages and from every shared link, and so does a `setup` Robot; only the per-Member render counter bounds it. That counter deletes rows older than `DAY_MS` and counts the rest (apps/worker/src/member/member.ts:984-991), i.e. a sliding 24-hour window, not "50 per Member a day" as the ticket and test comment put it (apps/worker/test/page-pdf.test.ts:3). *Severity: risk* (cost after Pause; drift in the limit's meaning).

13. **The safety net's step limit cannot deliver its documented closing step, and its step runs with no tool allow-list.** `SAFETY_NET_STEPS = 3` is documented as "a say, and its closing answer" (apps/worker/src/agent/say.ts:53-54), but `platformStep` cancels the agent as soon as the *n*th `step/start` is seen (apps/worker/src/agent/platform-step.ts:91-93), so the third request is aborted at its start and only two can complete. The same counter governs the dream's "at most 12 steps" (robot.ts:784-786; docs/issues/mr-robot-v1.20/05-dreaming.md: "A step counter cancels it at 12 model steps"). The safety net also passes no `tools` (apps/worker/src/plugins/say.ts:50), so during it every granted tool is callable — including Box and Host commands, Exa and send tools — which is intended for "speak now" but means a silent owner Turn can run arbitrary work after its last step, with the fallback text taken from any of it. *Severity: drift/note*.

14. **A requires-hosts test passes without exercising its claim.** "only the Hosts the Robot holds a facet on count (ob-5nvd)" pairs Desk and Studio, holds a facet on Desk only, drops Studio and asserts the Task still runs (apps/worker/test/requires-hosts.test.ts:143-152). A gate that ignores Hosts entirely, or that loses the facets, passes it just as well; nothing in the test asserts that a held Host's outage *does* stop a Task. That other half lives only in the later "counts only the Hosts where Mr. Robot's owner raised a facet" test (line 243-266), which is the one the implementer reported flaky. *Severity: test gap.*

15. **The two tests the implementer named fail on timing, and one of them passes vacuously when the alarm does not run.** In requires-hosts the Host's offline state is assumed after a fixed `pause(100)` on socket close (apps/worker/test/requires-hosts.test.ts:49), the "fresh instance" test aborts every Durable Object and then calls `runDurableObjectAlarm` without checking its return (line 260-262, helper at 84-89); under load the close or the alarm can be later than the test assumes, and if the alarm did not run at all the attempt assertion fails. In the Box spend test the limit's arrival in the registry is awaited with `vi.waitFor(..., { timeout: 10_000 })` and the comment admits it: "The limit check after the stop reaches the registry a moment later under load" (apps/worker/test/box.test.ts:154-159); it also assumes the stop's usage row is written before the panel is read (line 155-157). *Severity: test gap* (flaky, as reported).

16. **Many "no change" assertions in requires-hosts would pass if the alarm did nothing.** `runDurableObjectAlarm`'s boolean is discarded everywhere (helper at apps/worker/test/requires-hosts.test.ts:84-89), so "a later alarm does not run it again" (169-171), "the Host's return finds nothing left to run" (189-193) and "a parked Task that was run now gets no second Turn" (280-284) cannot distinguish "the robot correctly declined" from "the alarm never executed". *Severity: test gap.*

17. **Typecheck and the dependency lint have holes at the edges of the workspace.** `pnpm typecheck` compiles apps/worker, apps/web, apps/host, packages/host-protocol and infra (package.json:16), but not `packages/protocol` (it has its own tsconfig and is only checked transitively) and not `scripts/` at all, so `scripts/dependency-lint.ts` and the other scripts are untyped. `lint:deps` detects Effect imports in DSH sources only with a static `from "effect"` / dynamic-import regex (scripts/dependency-lint.ts:44-47), which misses `require('effect')` or a re-export, and its Node-bound list is hand-maintained (lines 21-27). The web-tree rule walks only `@mr-robot/web` (lines 50-61). *Severity: note.*

18. **Migrations run on every boot, some outside a transaction.** The Member Durable Object merges `usage` rows from source `computer` into `box` and deletes the old rows in every constructor, as two separate statements (apps/worker/src/member/member.ts:739-740) — an interruption between them would re-add the same cost on the next boot, double-counting a month's usage. The Space runs `renameHomeMemory`, `migrateSpendLimits`, `migrateBrowserBackends` and `renameHomeValues` in every constructor (apps/worker/src/space/space.ts:1389-1392, 1408), and `renameHomeMemory` uses `UPDATE OR IGNORE` (space.ts:1340-1343), so when both `home-md` and `space-md` exist the old row is left behind forever and the next boot tries again; `migrateBrowserBackends` deletes three settings on every boot (space.ts:1915-1922). Robot storage is versioned and runs once (apps/worker/src/robot/store.ts:515-529), so the asymmetry is in the Member and Space objects. *Severity: note/risk.*

19. **The help-Ask Mr. Robot path is now unreachable, but its route, docs and override branch remain.** `MR_ROBOT_ASKS` is an empty set (apps/worker/src/robot/programs.ts:583) and `answerHelp` calls `mayAnswer` with the answerer, so a `help` Ask can be answered only by the owner; the "owner answers after Mr. Robot" branch (programs.ts:969-972) and the `answerer.by === 'mr-robot'` path can never run, while `/api/robots/:id/help/:request` and the closing note ("Mr. Robot's answerer is checked against the Ask's kind") still describe them. *Severity: drift* (dead code and a contract that no longer exists).

20. **A Member the Robot is shared with can stop its Box.** `POST /api/robots/:id/box/stop` guards with `reach` (apps/worker/src/edge/api.ts:822), which admits `shared` as well as `owner`, unlike every other destructive Box action (`/box/jobs/:job/stop` uses `owner`, line 824). A Stop syncs the kept folder and then bills the running time (robot.ts:930-953), so a viewer can force both. *Severity: note.*

## What was checked and found sound

- The Box token: signed before a Robot is named (apps/worker/src/index.ts:33-38), compared against the live record and the container (apps/worker/src/places/box-door.ts:48-50), re-minted at each boot (robot.ts:874, 895) and dead once the Box is off; a permit covers exactly one key and one direction (apps/worker/src/places/copy-permit.ts:51-75).
- Shared-page door: unsigned, altered and out-of-shape tokens name no Durable Object; revocation reaches the Member and never the Robot (apps/worker/test/shared-page-door.test.ts:36-64).
- Webhook key: checked constant-time before the body is read, bounded bodies and Idempotency-Keys (apps/worker/src/edge/hooks.ts:47-69; apps/worker/test/webhook.test.ts:79-113).
- The ten-minute steer is one per owner Turn and is cleared by a say or a Turn end (apps/worker/src/plugins/say.ts:61-78; apps/worker/test/say.test.ts:261-289).
- "Always allow" is refused for a review denial and for an escalated call (apps/worker/src/robot/store.ts:1170-1178), and Mr. Robot cannot answer any Ask (programs.ts:578-588).
- A Subagent cannot create an Ask: the gate throws for any session but the live one (apps/worker/src/robot/robot.ts:1470-1477), and the test covers it (apps/worker/test/subagents.test.ts:115).
- Cold chapters upload before deleting, in a transaction (apps/worker/src/robot/cold-chapters.ts:48-56); a crash in between re-uploads.
