# Review: Mr. Robot v1.19 code — chapters, the stored chat, the Trajectory per chapter, Rewind, cold chapters, the scale test

Subject: `docs/issues/mr-robot-v1.19.md`, its tickets 01–07 and closing notes, and the code of commits `08a530e` `1d4a081` `1c3da16` `5aee8d4` `0476e3a` `ed1f012` `fdb0e60`.

Method: read the spec, all seven tickets and their closing notes, `GLOSSARY.md`, the ADRs, `apps/worker/src/robot/{chapters,cold-chapters,projection,chat-items,views,store,programs,robot,subagent-store,deputy}.ts`, `apps/worker/src/agent/{chapter-seed,session-log,conversation-search,compaction,memory,compose}.ts`, `apps/web/src/components/{ChatScroll,ChatView,ChapterBar}.tsx`, `apps/web/src/components/chat-pages.ts`, `apps/web/src/App.tsx`, `apps/web/src/pages.tsx`, `apps/web/src/dsh/RobotTrajectory.tsx`, the protocol shapes, and the tests named below. I ran the Worker suite; it is green (122 files, 728 tests, including `scale.test.ts`). Nothing was edited.

Read-only review. No recommendations. Severities: **bug** (wrong now), **risk** (wrong under a condition I name), **drift** (spec and code disagree), **test gap**, **note**.

Counts: bug 1, risk 7, drift 2, test gap 2, note 9. Total 21.

The three most serious: finding 1 (a Rewind into or across a cold chapter computes its "external effects since then" label only from SQLite rows that cold storage has deleted, so the model can be told nothing happened), finding 2 (Clear history deletes the local chapter and chat before awaiting the R2 deletes, so an eviction or an R2 error in that window leaves the Robot with no chapter, an empty chat and a 404 Trajectory), finding 5 (a chapter that goes cold before its first search is skipped by the index and the `*all-indexed*` sentinel makes the skip permanent).

1. **What.** The Rewind's external-effects label is built only from `session_event` rows, and cold chapters have no such rows. `toolsSince` runs one `SELECT ... FROM session_event` per chapter; `moveColdChapters` deletes those rows. A Rewind into a cold chapter (allowed: `rewind` reads the chapter through `logOf`, and the PWA offers Rewind on a cold chapter because only `superseded` hides it) therefore gets a label that omits every tool the Robot called after the point; if the target chapter itself is cold and no later chapter is hot, the label says "no tool was used since then". The model can then repeat a send, a payment or a file write the label exists to prevent.
   **Evidence.** `apps/worker/src/robot/programs.ts:1057-1063` (`toolsSince`: `SELECT DISTINCT json_extract(event, '$.data.name') ... FROM session_event WHERE session_id = ? AND seq > ?`); `apps/worker/src/robot/cold-chapters.ts:52-55` (`DELETE FROM session_event WHERE session_id = ?` for the chapter and its Subagents); `apps/worker/src/robot/programs.ts:1026` (`const events = yield* logOf(target.sessionId)`, which reads R2) beside `:1037` (`toolsSince(store, target.sessionId, atSeq, later...)`); `apps/web/src/pages.tsx:116` (`canRewind = ... shown?.superseded !== true`). Spec `docs/issues/mr-robot-v1.19.md`, Rewind: "the fact that external effects since the point still stand delivered as the label of my next Wake-up" (ec-utsf); ticket 05 closing note: "the tools being those called after the point in that chapter and in every chapter it supersedes (read with one SQL query per chapter, no JSON parsing)".
   **Severity.** bug.

2. **What.** Clear history deletes `chapter`, `chat_item`, `chat_fold` and the session tables first, then `await`s the R2 deletes, and only then switches `liveSessionId` and opens a new chapter. If the DO is evicted during that await (it is one R2 list/delete round trip per 1 000 objects) or `deleteColdChapters` throws, the local history is gone, the old cold objects survive, and the Robot is left with no `chapter` row for its live session: `GET conversation` answers 200 with no items (the newest-page query has nothing to start from), `GET trajectory` answers 404, and the next Turn's events are appended to a session with neither a chapter nor a chat fold, so they never reach the chapter chain, the chat or the Trajectory until a later compaction opens a *new* chapter (which leaves them behind for good). The old cold objects also survive the operation that was meant to remove them.
   **Evidence.** `apps/worker/src/robot/robot.ts:504-517`: `for (const table of [...'chapter', 'chat_item', 'chat_fold'...]) sql.exec(...)` at :505, `this.store.search.clear()` at :508, `await deleteColdChapters(...)` at :510, `const next = this.store.updateConfig(...)` at :512, `this.store.openChapter(...)` at :513. Read side: `apps/worker/src/robot/views.ts:147` (`store.chapters.latest(1)[0]`), `:367` (`chapterOf` → `notFound`), `apps/worker/src/robot/chat-items.ts:96-99` (`extend` returns when `chapters.get(sessionId)` is undefined), `apps/worker/src/robot/robot.ts:1364` (`rollChapter` only for the `CHAPTER_COMPACTED` session). Spec: "delete, Clear history, Start over and Reset everything to cover cold chapters too, so that nothing survives that should not" (ec-cgsl).
   **Severity.** risk — a DO eviction or an R2 error in that window.

3. **What.** Two chapters can be opened from the same parent. `rollChapter` reads `this.store.get(CHAPTER_COMPACTED)` and the running-Turn/Subagent condition, then `await`s `releaseComposition()`, and only afterwards builds the seed and writes the transaction that closes the chapter, opens the new session and deletes the flag. The idle compaction calls `rollChapter` at the end of `idleCompact`; the next Turn calls it at its start, before `beginTurn`, when `activeTurn()` is still `undefined`. A Wake-up arriving inside that await (the idle path can be in flight for minutes) passes both conditions in both calls; whichever transaction runs second uses its stale `from`, no-ops the close (`WHERE closed_at IS NULL`), opens a second chapter with the same parent and overwrites `liveSessionId`. The first new chapter is then an unclosed, non-superseded second "live" chapter: `chain()` and `views()` list it as live, the chat walks both, and the Turn that was running on the first new session is missing from the model's new context (the surviving chapter's seed was taken before it ran).
   **Evidence.** `apps/worker/src/robot/robot.ts:1363-1393` (`const from = ...` at :1363, the flag check at :1364, the Turn/Subagent check at :1365, `await this.releaseComposition()` at :1367, which clears `this.composition` synchronously at :1989 so the second caller does not wait at all, `readStoredEvents`/`chapterSeed`/`Session.create` at :1369-1381, the transaction at :1382-1392, `store.delete(CHAPTER_COMPACTED)` at :1390); `apps/worker/src/plugins/idle.ts:154-160` (`idleCompact` ends with `await host.rollChapter()`); `apps/worker/src/robot/robot.ts:744` (`if (!resuming) await this.rollChapter()` before `beginTurn` at :757); `apps/worker/src/robot/robot.ts:832` (the same call at the Turn's end); `apps/worker/src/plugins/idle.ts:78` (`idleNow()` is checked once, before `idleCompact` runs).
   **Severity.** risk — a Wake-up arrives while the idle close is between its check and its transaction.

4. **What.** A Rewind is not atomic against a Wake-up. `rewind` checks `working()` once, then `await`s `logOf` (an R2 fetch for a cold target) and `releaseAgent()` before its transaction. `working()` is false for a queued Wake-up, so `wake()` → `drain()` can start a Turn in that window, in the still-live chapter. The Rewind's transaction then closes that chapter (cut at the point) and switches `liveSessionId`; the running Turn keeps appending to the old session, `beginTurn` recorded the old session, and when it ends its `rollChapter` sees a `CHAPTER_COMPACTED` for a session that is no longer live. The owner's message and the Robot's reply land after the cut: `chat.page` filters them out (`seq <= cut`), the new live chapter's seed never saw them, and the model goes on as if neither existed. The external effects of the Turn did happen.
   **Evidence.** `apps/worker/src/robot/programs.ts:1022` (`if (yield* platform.working()) return yield* conflict(...)`), `:1026` (`yield* logOf`, R2 when cold), `:1040` (`yield* platform.releaseAgent()`), `:1041-1051` (the transaction), `:1046` (`branch(target.sessionId, atSeq, now)`); `apps/worker/src/robot/views.ts:154` (`(chapter.cut === null || row.seq <= chapter.cut)`); `apps/worker/src/robot/programs.ts:1045` (`close(current.liveSessionId, 'rewind', ...)`); `apps/worker/src/robot/robot.ts:292` (`working: () => ... activeTurn() !== undefined || this.pumping !== undefined` — queued wake-ups are not "working"). Spec: "Rewind without a ghost ... the seed is real history up to the point" (ec-i74p/ec-utsf).
   **Severity.** risk — a Wake-up or steer arrives in the window between the `working()` check and the transaction.

5. **What.** A chapter that goes cold before it has ever been indexed is never indexed and the sentinel then hides it forever. `registerChapters` creates the chapter rows without `search.track`, so every chapter of an upgraded Robot has no `chat_search_state` row; `moveColdChapters` does not index before deleting the events. The first search calls `catchUp(liveSessionId)`, then `catchUp(chapter.session_id, chapter.first_seq)` for the `behind` chapters — for a cold one `session_event` is empty, so `catchUp` records `next_seq = first_seq` and returns, and `search` writes `*all-indexed*` and never looks again. Every future search silently misses those chapters. The natural sequence (upgrade, the first Turn's tidy pass moves the old chapters once the backfill has folded their chat, the owner searches later) reaches it without any error.
   **Evidence.** `apps/worker/src/agent/conversation-search.ts:60-62` (`track`), `:70-90` (`catchUp` reads `session_event`), `:108-116` (`behind` query, the loop, then `INSERT OR REPLACE ... '*all-indexed*'`); `apps/worker/src/robot/chapters.ts:180-215` (`registerChapters` inserts chapters only); `apps/worker/src/robot/cold-chapters.ts:41-59` (no search call); `apps/worker/src/robot/robot.ts:834` (the backfill is a separate step from the tidy pass at `:745`, which is what moves cold chapters). The test that covers search with cold chapters searches a Robot whose every chapter was tracked at creation: `apps/worker/test/cold-chapters.test.ts:73`. Spec: "conversation_search and the chat search to cover every chapter, so that nothing is lost to the chain" (ec-enqy).
   **Severity.** risk — an upgraded Robot whose old chapters move cold before its first search.

6. **What.** The Rewind's label never looks at Subagent sessions. `toolsSince` scans the target chapter and the later chapters; Subagent logs are separate `sa-` sessions that belong to a chapter (`subagent.parent_session`) but are not chapters themselves. A Rewind that goes back before a delegation therefore reports only the Robot's own tool names, never the Subagent's `say`, `write`, `box_run` or Host calls. A Subagent started before the point is not stopped by the Rewind either: only delegations at or after the point are archived and cancelled.
   **Evidence.** `apps/worker/src/robot/programs.ts:1058-1062` (the two `session_event` queries, both over chapter session ids from `store.chapters.chain()` at :1036); `apps/worker/src/robot/cold-chapters.ts:48-49` (Subagent logs are held beside the chapter, but read here only for R2); `apps/worker/src/robot/subagent-store.ts:42-47` (`parent_session`, no chapter row); spec ec-utsf and ticket 05's note ("the tools being those called after the point in that chapter and in every chapter it supersedes").
   **Severity.** risk — a Rewind whose window contains a delegation; the label can say "no tool was used since then" while the Subagent wrote files or sent messages.

7. **What.** A live chapter's close is deferred by *any* running Subagent, not only one of its own, and it is deferred to a Turn boundary. `rollChapter` returns while `subagentRows.running().length > 0`; a long delegation started in the chapter therefore keeps the chapter open across later Turns and later compactions, and its log grows past one context budget. The resume measurement in ticket 02 (373 rows, "the agent resume reads 373 rows from the live chapter") is a live chapter of that size; nothing bounds a chapter whose close was deferred, so "waking costs the same on day one and day 400" (ec-7s3l) rests on a condition the code does not enforce.
   **Evidence.** `apps/worker/src/robot/robot.ts:1365` (`if (this.store.activeTurn() !== undefined || this.subagentRows.running().length > 0) return`); `apps/worker/src/robot/robot.ts:1306-1318` (a running Subagent survives a restart while its parent is the live chapter); `apps/worker/src/agent/session-log.ts:204-208` (`read` returns the whole stored log from `offset`); `docs/issues/mr-robot-v1.19/02-chapters.md` closing note ("The chapter closes at a Turn boundary ... only when no Subagent runs in it"). Spec: "a chapter is at most a context budget long by construction" (Solution, Chapters).
   **Severity.** risk — a long-running Subagent keeps the chapter open.

8. **What.** The deputy's numbered pages are quadratic. `conversationPage(page)` starts from the newest cursor on every iteration and walks `page` pages, each a separate `chatRows` query, so page N reads about 21 × N rows; the page number comes from a tool parameter with no cap (`robot_conversation page`). The scale test measures `conversationPage(2)` only. On a year-old Conversation a page deep in the chat turns into thousands of statements in one RPC, and the cost per page grows with the Robot's age, which is the property the spec's story 8 forbids for a page.
   **Evidence.** `apps/worker/src/robot/views.ts:268-291` (`for (let index = 1; index <= number; index += 1) rows = chatRows(...)`); `apps/worker/src/agent/tools/deputy.ts:51`, `:68-70` (`page` declared `{ type: 'integer' }` with no maximum); `apps/worker/test/scale.test.ts:132-134` (`conversationPage(2)`); ticket 03 closing note ("The deputy's numbered pages walk the same cursor"). Spec: "opening a chat and loading a page to read a bounded number of rows regardless of the Robot's age" (ec-yxru).
   **Severity.** risk — a deep page request (for example a Robot diagnosing an old failure), unbounded by the tool.

9. **What.** The PWA's own chat search does not use the server index; it scans the loaded items and loads at most 40 more pages per "Previous" press, and it shows "none loaded" with no progress when the match is farther back. "The chat search covers every chapter" (ec-enqy) holds only after enough presses, and nothing tells the reader a match still lies beyond; a search for a word in a year-old chapter reads up to 2 000 items per press with the reader driving each one.
   **Evidence.** `apps/web/src/App.tsx:208-225` (`matches` from `items` only; `older()` loops `page < 40`; "none loaded" at :242); `apps/worker/src/robot/views.ts:338-350` (`searchConversation`, the server path, unused by the chat search); `apps/web/test/chat-pages.test.tsx:78-86` (the test reaches the word after three pages).
   **Severity.** drift — the ticket's "the chat search ... cover every chapter" (ec-enqy) is met only through repeated manual page loads.

10. **What.** The spec's cold-storage decision fixes the object path and the column the move marks; the code uses both differently. The spec says "R2 under `<robot>/chapters/<ordinal>.json` (events only)" and "deletes their session_event rows and marks the `session_log` row cold"; the code writes `chapters/<robot id>/<ordinal>.json` and sets `chapter.cold` (the `session_log` row is left untouched, length included). The ticket's closing note documents the path change and states the opposite of the spec's second half ("The chapter row, session_log row, chat items and search rows stay"), so the spec's "marks the session_log row cold" is contradicted by the implementation and quietly superseded by the ticket.
   **Evidence.** `docs/issues/mr-robot-v1.19.md` (Implementation Decisions, Cold storage); `apps/worker/src/robot/cold-chapters.ts:22-26` (`coldPrefix`/`coldKey`); `:52-55` (events deleted, `markCold`); `apps/worker/src/robot/chapters.ts:166-168`; `docs/issues/mr-robot-v1.19/06-cold-chapters.md` closing note ("The objects are at chapters/<robot id>/<ordinal>.json, beside the Workspace and outside it").
   **Severity.** drift (documented in the ticket for the path; the `session_log` mark is not).

11. **What.** The stored chat is seeded for the scale test through a test-only call, not through the production wiring. `seedYearForTest` opens the bare `SqliteSessionLog`, appends each span and then calls `this.store.chat.extend(...)` itself; the production path is `onStored`, called inside the append transaction by `SqliteSessionLog.write` (`apps/worker/src/robot/robot.ts:2024-2026`). Both call the same `extend`, but if the composition stopped passing `onStored`, or passed the wrong session id, every scale budget would still pass while a real Robot stored no chat at all. Only `chat-items.test.ts` covers the production wiring, with a handful of Turns.
   **Evidence.** `apps/worker/test/worker.ts:194-200` (`await handle.append(...)` then `this.store.chat.extend(live, batch[0]!.seq, ...)`, with the comment "this log is the seam's bare adapter"); `apps/worker/src/agent/session-log.ts:186` (`this.onStored?.(id, stored.length)`); `apps/worker/src/robot/robot.ts:2024-2026`.
   **Severity.** test gap.

12. **What.** Two paths the budgets are meant to guard are not measured by any test: the first Trajectory listing of an *upgraded* Robot, and a Rewind into or across a cold chapter. `ChapterStore.views()` counts the Turns of every closed chapter with `turns === null` and writes each count back, so the first listing after `registerChapters` runs one `COUNT(*)` and one `UPDATE` per chapter (two statements per chapter; for a year-old Robot hundreds), and that first request is what the owner sees after the deploy. The scale test seeds its chapters through the real close, which stores `turns`, so `views()` never enters that branch there. No test rewinds into a cold chapter, which is exactly the case findings 1 and 6 are about.
   **Evidence.** `apps/worker/src/robot/chapters.ts:139-152` (`if (turns === null) { ... COUNT ... UPDATE }`); `apps/worker/src/robot/chapters.ts:180-215` (`registerChapters` inserts `turns` as NULL); `apps/worker/test/scale.test.ts:137-146` (the Trajectory budget, seeded through `rollChapter`); `apps/worker/test/chapters.test.ts:138-159` (the upgrade test lists two chapters, no budget); `apps/worker/test/cold-chapters.test.ts` (no Rewind).
   **Severity.** test gap.

13. **What.** Turn counts and the Rewind's tool names are read from the serialized event with a prefix `LIKE`, so they depend on the key order `JSON.stringify` happened to write. Both queries match `event LIKE '{"type":"...' `; an event stored with a different key order (another writer, a future serializer, a hand-edited row) counts as zero Turns and as no tool use, silently. The chat readers parse the JSON and are immune; these two are not.
   **Evidence.** `apps/worker/src/robot/chapters.ts:144` (`event LIKE '{"type":"turn/start"%'`); `apps/worker/src/robot/programs.ts:1060` (`event LIKE '{"type":"tool/call"%'`); `apps/worker/src/agent/session-log.ts:181` (`this.redact(JSON.stringify(event))` — `maskSecrets` replaces substrings and keeps the order, `apps/worker/src/agent/tools/secrets.ts:38-46`).
   **Severity.** note.

14. **What.** After a chapter moves cold, its `session_log.length` and `chat_fold.next_seq` keep their old values while its rows are gone. `storedLength()` still reports the old length, `ChatItems.current()` is true only because of that, and `SqliteSessionLog.read(id)` would return fewer events than the header and the snapshot claim. Today every reader of a cold chapter goes through `logOf`/R2 or `chat_item`, so the invariant is inert — but it is broken, and any future reader that trusts `session_log` (a resume, an export, a diagnostic) gets a truncated log with no error.
   **Evidence.** `apps/worker/src/robot/cold-chapters.ts:52-55` (only `session_event` is deleted); `apps/worker/src/agent/session-log.ts:78-80` (`storedLength`), `:204-208` (`read`); `apps/worker/src/robot/chat-items.ts:75-78` (`current`), `:96-99` (`extend`).
   **Severity.** note.

15. **What.** A cold chapter whose R2 object is gone renders as an empty chapter, not as a failure. `coldChapter` returns `undefined` when `bucket.get` is null, and `logOf` then falls back to `readStoredEvents`, which reads the deleted rows and returns `[]`. The Trajectory page answers 200 with no events, `trajectoryAround` finds nothing, and the chapter's Subagent logs are empty too. "Cold is slower to open but never gone" (ec-aly5) holds only while the object exists, and nothing distinguishes a lost object from a chapter that never had events.
   **Evidence.** `apps/worker/src/robot/cold-chapters.ts:61-68`; `apps/worker/src/robot/programs.ts:125-133`; `apps/worker/src/robot/robot.ts:478` (`deleteColdChapters` in `destroy`, before `deleteAll`, so a failure leaves the rows that point at the objects it already removed).
   **Severity.** note.

16. **What.** The chat backfill's sentinel is decided by the number of events folded, not by whether chapters remain. A chapter whose slice yields no events (a data inconsistency, or a chapter left behind by a lost `chat_fold` row) is skipped without advancing `done`, the loop finishes, `done < budget` writes `*all-folded*`, and `backfill` returns 0 forever afterwards. That chapter is then folded in memory on every page — from an empty log if its events are gone — and no page ever repairs it. With the present cold-move condition (a chapter must be `current` before it moves) the scenario needs an inconsistent row, but the sentinel logic turns any single skipped chapter into a permanent one.
   **Evidence.** `apps/worker/src/robot/chat-items.ts:123-147` (`behind` at :125-129, `events` at :136, `done += events.length` at :143, `if (done < budget) this.save(ALL_FOLDED, ...)` at :145), `:124` (`if (this.foldOf(ALL_FOLDED) !== undefined) return 0`), `:153-164` (a chapter that is not current is folded whole, in memory, on each page); `:114` and `apps/worker/src/robot/cold-chapters.ts:45` (`if (!store.chat.current(...)) continue`).
   **Severity.** note.

17. **What.** A Notice, an Ask or a delegation row added beside the log is two statements outside a transaction, and `addNotice` relies on the first one having succeeded: when `chat.side` returns true it does not write the fallback `notice` row. An eviction between the `chat_item` insert and the `chat_fold` update leaves a row the fold does not know about, and the next side row or append overwrites that position; the notice is lost from the chat with no other copy. `propose` ignores `side`'s result the same way.
   **Evidence.** `apps/worker/src/robot/chat-items.ts:111-117` (`rows.put` then `this.save(...)`, no transaction); `apps/worker/src/robot/store.ts:981-985` (`addNotice` returns as soon as `side` is true); `apps/worker/src/robot/store.ts:731-733`.
   **Severity.** note.

18. **What.** After a Rewind, an Ask raised after the point stays open everywhere the product looks for open Asks, though its chapter is superseded and its card is hidden. The proposal table is global, `GET conversation` ships `store.proposals('open')` as `asks` on every page, and the Fleet state counts open proposals; the Rewind touches no proposal. The owner can answer a question whose card they cannot see, the Fleet keeps saying "waiting for you" for a chapter the Robot no longer sees, and the answer arrives as a wake-up about a question the model's chapter never contained.
   **Evidence.** `apps/worker/src/robot/store.ts:703-708` (`proposals('open')`); `apps/worker/src/robot/views.ts:255` (`asks: store.proposals('open')...`), `:89` (`waiting for you`); `apps/worker/src/robot/programs.ts:1018-1055` (no proposal handling in `rewind`); GLOSSARY `Superseded chapter` ("off the Conversation; the Robot does not see it").
   **Severity.** note.

19. **What.** `rewind(atSeq)` can cut between an Ask's tool call and its result, and the seed deliberately drops that call: the new chapter has no record of the question, while the proposal stays open and its answer is delivered later as `askAnswer`. The Rewind sheet only cuts before a Turn, so this needs the API's `atSeq` ("The point must be one of the chapter's own events", ticket 05) — but the endpoint accepts any event, and the seed is then less than "what the model saw at the point".
   **Evidence.** `apps/worker/src/agent/chapter-seed.ts:34-44` (the open call is found and the surface is sliced before it); `apps/worker/src/robot/programs.ts:1027` (`atSeq` may be any index of the chapter's own events); `apps/worker/src/robot/robot.ts:1414` (`askAnswer` rides the next platform Wake-up); ticket 05 closing note ("When the point falls between a tool call and its result, the seed ends before that call, so the model never sees a call without an answer").
   **Severity.** note.

20. **What.** `RewindView.undone` and the `rewind.undone_at` column survive the removal of undo. `rewind` still writes the field as `false`, the protocol still carries it, and the store still reads the column (the upgrade's `closedAt` even consults `undone_at`). Nothing can set it any more, so the shape advertises an operation no endpoint offers.
   **Evidence.** `apps/worker/src/robot/programs.ts:1054` (`{ ...record, undone: false } as RewindView`), `:1038` (the record fields); `apps/worker/src/robot/chapters.ts:193`, `:204` (`undone_at` in the upgrade); `apps/worker/test/rewind.test.ts:140-144` (undo answers 404).
   **Severity.** note.

21. **What.** The PWA keeps one `EventWindow` and one kept-alive atom per chapter a reader visits (`sourceKey = "<robot>#<ordinal>"`), and each window holds every event it loaded; the window and atom are never released. A reader who pages through a year of chapters of a large Robot keeps each chapter's events (up to 2 000 per page load) in the page for the life of the tab, and the maps survive chapter switches and remounts. This is a browser-memory cost that grows with the number of chapters read, not a correctness failure.
   **Evidence.** `apps/web/src/dsh/RobotTrajectory.tsx:108-118` (`windows` map, `Atom.family(...).pipe(Atom.keepAlive)`), `:87-89` (`events` kept per window), `:173` (`window.events = [...page.events, ...window.events]`).
   **Severity.** note.

## Questions the review was asked, and what the code says

| Question | Answer | Findings |
|---|---|---|
| Can a chapter boundary lose or duplicate an event — compaction mid-Turn, a Subagent running, a steer during the close, a restart between seed and switch? | Mid-Turn compaction is faithful: the seed is the surface at the Turn's end, which is what the model saw (tested in `chapters.test.ts:54-92`). A running Subagent defers the close but does not lose events (7). A steer during the close is queued as a Wake-up and runs in the new chapter — no loss. The seed write, the close and the `liveSessionId` switch are one transaction, so a restart between them is not possible. But two concurrent closes can open two chapters over one parent (3), and a Rewind can switch the chapter under a running Turn (4). | 3, 4, 7 |
| Is the chapter seed faithful to what the model saw (system prompt, checkpoint, memory baseline, pending Asks)? | System prompt, the last checkpoint and the messages after it are re-appended in surface order, with a closed Turn and the inherited marker; the memory baseline survives the boundary because the marker follows the session (`chapters.test.ts:107-120`). Pending Asks are not carried: the seed slices them off (19). The Rewind path builds the same seed without a Turn boundary check beyond the open-call slice. | 19 |
| Does the backfill terminate and stay bounded per Turn? | Bounded at 4 000 events per Turn (`CHAT_BACKFILL_EVENTS`), newest chapter first; it terminates for normal chapters and the sentinel ends it when nothing is left (16).
