# Mr. Robot v1.15 — Grok Bot lessons

## Problem Statement

The owner compared Mr. Robot v1.14 with the leaked Grok Bot system prompt and tool catalogue (docs/research/grok-bot-capabilities.md covers the public documentation; the leak covers the behaviour) in a grill session on 2026-10-20. The architecture and the control surface of Mr. Robot are equal to Grok Bot's or ahead of it: steer and follow-up, Tasks, Grants per item, Auto review as an Ask, cost by source, Threads, Hosts, deputy. What Grok Bot has and Mr. Robot lacks is almost all behaviour: how the agent talks to the person, how it asks, how it shows its work, how it decides on its own, and how it uses its own harness. A few capabilities are missing too, each small.

1. **No voice of its own.** A Robot's reply is whatever assistant text the model emits. In code mode the model must write every character of a result it already holds in a variable; it cannot hand a file, a grep result or a screenshot to the owner by reference; it has no way to send three short messages at the right moments of one program; and nothing in the platform knows whether a Turn delivered anything.
2. **No question with options.** A Robot can only ask in prose, or through the special Asks (grants, reviews, tool calls, help). Grok Bot's question widget — one natural question, real options, a custom answer, a danger style — is the mechanism the owner wants to copy.
3. **Help goes through a timer.** need_help puts a request to the owner, waits 30 minutes, then wakes Mr. Robot. Grok Bot has no escalation at all; the session found that a question to the chief is a Robot message, and that the chief forwards what he cannot answer. Three tools and a timer stand where one default Grant would do.
4. **A Robot cannot ask for a login.** When a site needs credentials it does not have, the Robot can only say so; the owner must find the Logins page himself.
5. **Harness knowledge has no home.** How to pace Tasks, how to build a question, when to delegate, how to drive the browser, how to write on the owner's behalf: Grok Bot carries this in its prompt. Mr. Robot's prompt is short by design; the skill library is per Home and granted per Robot, so platform knowledge cannot live there.
6. **Box commands block.** A command on the computer waits up to thirty minutes and ends. A build, a long script or a watcher cannot run while the Robot does something else, and the Robot never hears that it finished.
7. **Small gaps:** no per-Connection usage instructions; no binary copy between a Host and the Workspace without passing through the model's context; a Robot cannot change its own title or avatar after setup; external text in tool results is not marked as such; the word "Computer" names the Robot's container while "computer" is what people call the owner's machine.

## Solution

**One voice: say.** Every Robot has a tool `say` that is its only way to speak to people. `say` takes text and optional attachments (Workspace paths, screenshot ids); each call is one message in the Conversation, shown at once, and goes out on the Channel the Wake-up came from (or the Channel named in the call). Assistant text stays in the Trajectory and is no longer shown as a reply. Because the voice is a tool, a code-mode program sends several messages at the right moments of one step, hands over a file or a result by reference, and the platform knows what a Turn delivered. A safety net covers the Turn that forgets: a Turn the owner caused that ends without `say` gets one bounded step to speak; if it still says nothing, the last assistant text becomes the reply, marked as a fallback. A Turn the owner caused that runs ten minutes without `say` gets one platform steer. Turns caused by Tasks, Robots and Subagents get the step and never the fallback: silence is a legal result there.

**Asking: one tool, one addressee.** `ask` puts one question to the owner in Grok Bot's shape: a natural prompt, optional help text, options with label, value, description and style, a custom answer when allowed, a dismiss-on-move-on flag for low-stakes questions, an urgent flag. It does not block: it stores an Ask of kind question and returns; the Robot goes on or ends its Turn; the answer wakes it as a steer with the chosen value, a dismissal wakes it with that fact and it does not ask again. A question to the chief is not an `ask`: every Robot holds a default recipient Grant to its owner's Mr. Robot, granted at creation and removable, and sends its question with `robot_send` marked as a question; Mr. Robot answers from what he knows or asks the owner and forwards the answer. The rule is one sentence: the chief may know, but may not consent. `need_help`, `help_requests`, `help_answer` and the 30-minute escalation go.

**A Robot asks for a credential.** `request_credential` creates an Ask of kind credential that carries the Login entry form (or a secret form) in the Robot's Conversation; saving it creates the entry under the owner, grants it to the Robot and wakes the Robot. The password never reaches the Robot's program.

**Platform skills.** The Worker ships read-only skills under docs/skills/, listed in the platform prompt one line each and loaded with the skill tool: tasks-cadence, asking, subagents, browser, channels, writing-as-owner. They need no Grant; the ones about a tool group show only to a Robot that holds the group. The platform prompt itself is rewritten to carry the rhythm of talking (reply first, keep posted, deliver), the voice (length, tone, no em dash, mirrored emoji, no headings in chat, lead with the result), autonomy with its two exceptions, initiative, and the ladder of sources; it stays short.

**Box, with jobs.** The Robot's container is renamed Box everywhere: grant, tools (`box_run`, `box_read`, `box_write`), Workspace folder box/, docs, UI, usage source. `box_run` behaves like DSH's bash: it waits in the foreground up to its limit, then the command goes on as a job in the background; `run_in_background` starts a job at once; `job_list`, `job_output` (with wait) and `job_kill` manage jobs; a finished job wakes the Robot as a follow-up with its exit code and the tail of its output, the whole output under spill/. The Box stays up while a job runs and the Robot's Turn may end.

**Small gaps closed.** A Connection carries custom instructions the owner writes; a Robot granted the Connection reads them in its prompt. `host_copy` copies a file between a Host and the Workspace in either direction without passing through the model. `set_identity` works after setup for title, description and avatar colour. Tool results that carry text from outside (web, Exa, Gmail, Slack, Discord reads, browser observation) are fenced as external data with their source named. The glossary and the product docs follow.

## Implementation Decisions

- **say.** A tool mounted in every Robot composition without a grant item, in code mode and direct mode; absent from Subagent child presets. Arguments: `text` (Markdown), `attachments?` (strings: a Workspace path, or `screen:<id>` for a stored screenshot), `channel?` (a Channel address the Robot may speak on; today a Discord channel the owner enabled). The call writes a session tool event; the Conversation projection makes a `reply` item from each say call (text, attachments, the event's time) and no longer from `assistant/message` events; the Trajectory keeps assistant text as today. Attachments resolve through the existing Workspace file API (the PWA renders image content types inline, other types as a file card); screenshots through the existing screen store. A reply item carries `fallback: boolean` for the safety net.
- **Channel output.** The Channel seam's output kind `reply` is emitted per say, not once per Turn; routing is unchanged: the Turn's cause route when the Wake-up had one, else the Channels that opted into unprompted output, else nothing; an explicit `channel` overrides. Discord uploads an attachment when the file is under its size limit, else posts a link into the app. The "finished" notification rule (never repeat a reply) stays.
- **Safety net.** The Turn record keeps `saidAt` (last say) and `cause`. At Turn end, when the cause is an owner Wake-up (owner message on any Channel, an Ask answer, a Takeover return the owner caused) and no say happened since the Wake-up: one platform step with a fixed instruction and a step limit (as the idle-compaction memory step); if the step ends without say, the last assistant text of the Turn becomes a reply item with `fallback: true` and a Trajectory note; when there is no assistant text at all, nothing is sent. For every other cause only the step runs. A DO alarm set when an owner Turn starts fires at ten minutes without say and injects one steer (`[Platform] <owner> has heard nothing from you for 10 minutes.`), once per Turn. Mr. Robot's messages to his staff are not owner causes.
- **ask.** A tool mounted in every Robot composition, absent from child presets. Arguments: `prompt`, `help_text?`, `options?` (`label`, `value?` defaulting to the label, `description?`, `style?` default | primary | danger, at most six), `allow_custom?`, `dismiss_on_move_on?`, `urgent?`. It stores an Ask of kind `question` and returns `{ askId, status: 'waiting' }`. The projection item kind `question` that today shows grant proposals is renamed `proposal`. The AskBar renders options as buttons, a text field when allowed, and Dismiss. An answer is queued as an owner Wake-up with steer delivery and the label `[Answer to ask <id>] <value>`; a dismissal `[Ask <id> dismissed]` with a sentence not to ask again; `dismiss_on_move_on` dismisses on the owner's next message Wake-up to that Robot with the reason "owner moved on". Push: urgent → "needs you" at once; otherwise the existing Ask notification path. Discord output of a question Ask: the prompt and a numbered list of options; answering from Discord is out of scope.
- **The chief question.** Robot creation (and a migration for existing Robots) stores a recipient Grant to the owner's Mr. Robot, kind recipient, ordinary in every way. `robot_send` gains `question?: boolean`; the delivered message is labelled `[Question from <robot>]`. No new tools. The tools need_help, help_requests, help_answer, the help plugin and the 30-minute alarm are removed; open help Asks keep their answer path until closed. Prompt: a Robot's "How you work" names the two addressees; Mr. Robot's role gains the answer-or-forward rule.
- **request_credential.** A tool mounted in every Robot composition, absent from child presets. Arguments: `kind` login | secret, `service`, `why`, `websites?`, `scope?`. It stores an Ask of kind `credential` carrying those fields. The AskBar renders the existing Login entry form (name, username, password, websites, scope, pre-filled) or the secret form (name, value, allow reading). Save: create the entry owned by the Member, grant it to the Robot at allow, queue an owner Wake-up `[Login "<name>" is available]` (steer); Decline: `[Credential request declined]`. The password field is write-only as today; login_fill is unchanged. Discord output: one line and a link.
- **Platform prompt.** Section `writing-style` becomes `talking` ("Talking to {owner}"); `how-you-work` gains autonomy, initiative, the ladder of sources and the app rules; `tools` gains the fence rule and loses need_help; a new section `platform-skills` lists the visible skills one line each; Mr. Robot's role gains the chief rule. Bound: the prompt for a Robot with every group granted stays under 2 800 words (measured by the existing prompt preview); the figure before and after goes in the ticket's closing note.
- **Platform skills.** Strings in the Worker like the product docs, under `docs/skills/<name>/SKILL.md` with a one-line description; `isDocsPath` covers them; the skill tool resolves a platform skill before library and local ones; the prompt index filters by tool group (subagents → subagents, browser → browser, channels → any Channel-bearing Connection or Discord). The texts are adapted from the Grok Bot leak (routines cadence, asking and widgets, subagent handling, computerUse and browserUse rules, channel pacing, writing-style matching) in the simple-english register of the product docs.
- **Connection instructions.** Column `instructions` on the Connection row, edited in the Connection's settings in the PWA and by the deputy connection tools; rendered in the runtime section as "- Instructions for <Connection>: <text>" for each Connection the Robot holds at allow or ask.
- **host_copy.** Tool in the host plugin, under the Host's file Grant: `{ host, direction: 'to_workspace' | 'to_host', host_path, workspace_path }`; the Host app streams the bytes over the existing Host channel in chunks; cap 100 MB; the result names both paths and the size. A Workspace path under `box/` reaches the Box at its next boot through the existing sync.
- **Box rename.** Grant item `tool:box`; tools `box_run`, `box_read`, `box_write`; Workspace prefix `box/` (migration renames `computer/`); usage source `box` (migration renames rows); docs/box.md; Robot panel "Box"; protocol and glossary words. The backend seam keeps its shape.
- **Box jobs.** `box_run({ command, timeoutSeconds?, run_in_background? })`. A command runs under `setsid` with stdout and stderr to `/workspace/.jobs/<id>.log` and its exit code to `/workspace/.jobs/<id>.exit`; the foreground wait polls the exit file up to the limit; on the limit the call returns `{ kind: 'promoted', jobId, output }`; with `run_in_background` it returns `{ kind: 'background', jobId }` at once; a command that finishes in time returns `{ kind: 'foreground', stdout, stderr, exitCode }` as today. A `jobs` table in the Robot DO (id, command, startedAt, finishedAt, exitCode, status running | completed | killed | failed | lost); a DO alarm every 15 seconds while jobs run checks exit files; a finished job copies its log to the Workspace `spill/jobs/<id>.log`, updates the row and queues a platform Wake-up (follow-up) `[Box job <id> finished: exit <n>]` with the last 40 lines. `job_output({ jobId, wait?, timeout_ms? })` returns the log since the Robot's last read (an offset kept on the row) or waits up to the timeout; `job_kill` sends SIGTERM to the session, then SIGKILL after five seconds. The idle stop alarm is not set while a job runs and starts from the last job end. On DO restart with running jobs the Box is probed: a job whose process is gone and has no exit file is marked lost and wakes the Robot as failed; a stopped Box marks every running job lost. The Turn may end with running jobs (the DO keeps itself awake only through the alarm, not waitUntil).
- **External fence.** A capability declares `external: true` on a tool (web_fetch, every Exa tool, gmail_search, gmail_thread, gmail_attachment, slack_* reads, discord_* reads, browser_observe); the tool registration wraps the rendered text result in `<external source="<tool>">` … `</external>` and rewrites any `</external` inside the content to `<\/external`. The prompt rule lives in `tools`.
- **Identity.** `set_identity` stays mounted after setup with `title?`, `description?`, `avatar_color?`; `name` is accepted only during setup. The reply rule: tell the owner what changed.
- **Compatibility.** Old session logs have no say events: the projection makes reply items from `assistant/message` for Turns recorded before the Robot's first say event (a per-Robot marker written at the upgrade), and from say afterwards.
- **Glossary** per gb-wz4o.

## Testing Decisions

A good test drives the system the way a person or a Robot does: through the edge API in workerd with the scripted model, or through a rendered PWA component with a stubbed API; the Box has one integration run on staging by hand. No unit test on plugin internals; no test touches the network except the staging run.

## Further Notes

Decisions from the grill session 2026-10-20 (five rounds), with what was weighed.

- **The leak is behaviour, not features.** The public research of 2026-10-09 compared capabilities; the leak showed that four fifths of Grok Bot's prompt is how to talk, ask, show work and decide. The owner wants those rules without Grok Bot's prompt length: the prompt stays short, practice goes to platform skills, and the models Mr. Robot runs are trusted to read them.
- **say was judged on its own merits.** The agent first called SendMessage a workaround for Grok Bot's lack of steer; the owner corrected this: in code mode a voice tool lets a program send the content of a variable, several messages per step, and files by reference, and gives the platform a fact about delivery. The dispatcher doctrine that surrounds it in Grok Bot was still rejected as a steer workaround.
- **One question tool, one addressee.** Grok Bot's widget is one question per call; DSH's batch exists because its call blocks. Mr. Robot's Asks never block, so a program asks several questions by calling ask several times. The idea of ask addressed to the chief was taken apart: it is a Robot message plus forwarding, and forwarding is the chief's ordinary behaviour; so the mechanism became a default recipient Grant and the rule "the chief may know but may not consent". need_help and its timer were removed as the second mechanism for the same thing. Grok Bot has no bot-to-bot escalation at all; its agents message each other fire-and-forget without grants, and a teammate's yes is never the user's.
- **Box.** The owner wanted the Robot's computer named as a thing of its own and the owner's machine kept as Host; jobs were pulled into 1.15 because DSH already has the shape and nothing is gained by waiting.
- **Fence now.** The owner chose to fence external results in this release rather than measure first; the fence is limited to tools that bring outside text, so the token cost falls only where the risk is.
- **Discord is the emergency channel.** Nothing in the app is limited by what Discord can show; Discord gets a text form of each new surface and a link.
- Seams: the edge API in workerd with the scripted model and the stub backends (Host, Box, Channel) for every behaviour; component tests for the new surfaces; one staging run. No new seam.
